# 审核方法与判定

在任务发现、分组派发、Agent 对照或 reference 消融时读取本文件。它约束证据记录和结论范围，不规定固定任务数，也不要求必须运行不可用的环境。

## 任务候选与覆盖映射

先记录审查产物版本和匹配的 DSH tag。按使用者提出的业务结果建立候选，而不是按包名或文档标题计数。优先查消费项目的实际需求、代码、问题记录和现有集成；再查目标版本公开导出和类型、教程、包 README、公开调用方、Profile 与行为测试。不同来源可合并为一项任务，但保留来源和差异。候选尚无公开可用路径时，写出已查证据和不确定性，不强迫产物覆盖目标版本做不到的事。

每项任务至少记录：用户要看到的结果、起始项目及约束、DSH 版本、任务来源、必需的公开入口、完成和失败判据，以及产物中的入口与目标小节。覆盖状态区分：可发现且路径完整、可发现但步骤不足、正文存在但难以发现、完全缺失、有证据的不适用、待核实。路由和链接通过只说明可达；还需检查读者能否在现有项目中确定依赖、初始化、配置或权限、装载、调用、资源清理及可观察验证。

候选发现不可能证明所有使用场景已穷尽。报告所查来源、发现的候选及未查来源，不把抽样结果外推成完整覆盖。

### 起点与可执行状态

对相关任务分别考虑两种起点：在目标 DSH checkout 内开发，以及从已发布包开始的独立消费项目。只有任务确实适用于某种起点才检查它，不把源码内教程自动视为可发布包教程，也不要求目标版本没有的公开能力。逐条沿 `SKILL.md`、路由、HOW-TO 和验证步骤核对：入口是否先让使用者识别起点；必需包、生成器、构建器和 Profile 安装步骤是否公开且可获得；限制是否在投入实现前可见。给每条适用路径标明“已运行验证”“仅类型或契约支持”“受阻”或“待核实”，并写明证据。正文承认构建受阻而路由仍呈现为完整可执行任务时，记录入口与正文的矛盾；示例给出了命令但未运行，不得标为已验证。

完成判据随用户目标确定。实现与接入要检查构建、装载、可观察行为和适用的失败、取消、卸载；静态评审可以在证据充分时交付有边界的审查结论；排错可以在根因已定位但修复尚未验证时交付定位结论，并明确修复状态。检查入口和路由是否把这些不同结论都强制套入同一个运行验收门槛，或反过来把仅有静态证据写成实现完成。

## 入口与 AGENTS.md

主 Agent 将本仓库根 `AGENTS.md`、分发 `skills/dsh-plugin-development/SKILL.md` 与 `skills/dsh-plugin-development/agents/openai.yaml` 作为“入口与治理”路径的三份独立审核文件。对根 `AGENTS.md` 逐项检查：创建源和生成产物的边界、版本与离线限制、事实优先级、验证与报告要求、授权规则，是否与现有创建流程和产物入口一致；是否存在冲突、过时说明或会误导审核与发布的规则。提出分发内容修改建议前，对照创建 Skill 与输出契约确认源文件归属、离线限制及版本标识规则；构建证据中的 commit 不能未经核对就建议写入分发文件。遵守现行 `AGENTS.md` 进行审核；审查某条规则不等于可以忽略它。

对分发入口检查：frontmatter 的名称和描述是否让正确的用户请求触发、无关请求不误触发；正文是否先核对版本，首屏任务链接与后续路由是否准确指向操作步骤，何时读取 API reference 是否明确，完成边界是否与实现、排错及评审的真实任务一致。首屏只突出一种起点时，检查其他适用起点是否能在投入构建前被识别；路由不能隐去 HOW-TO 已知的公开构建阻碍。对 `agents/openai.yaml` 检查展示名称、简述和默认提示是否与 frontmatter、版本和正文任务范围一致，以及有无改变调用策略的字段。用正向、反向和版本不符的真实用户措辞检验入口，记录触发、加载的文件和结果；只读文字时标为静态判断，不声称已经验证自动触发。发现不一致时引用双方位置并提出分别归属的改法。

根 `AGENTS.md` 不在分发目录，不能替代消费项目里缺失的任务指导，也不计入分发 reference 数。若实际消费项目有自己的 `AGENTS.md`，阅读其适用规则并记录是否与分发 Skill 的使用步骤冲突；把它作为独立的项目上下文，不计入本仓库文件总数，不未经用户要求修改该项目规则。没有消费项目时报告该交互未检查。

### 从用户请求检验触发

先从真实请求提取用户要达成的结果，不用 `SDK`、`Tool` 或 `Profile` 等词的出现次数代替意图。以用户常见的五类目标建立入口候选，再按本产物“固定版本的 DSH Cordis 插件开发”范围裁决：

| 用户目标 | 应检查的具体请求与预期边界                                                                                                        |
| -------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 接入     | 将 DSH 插件包接入现有项目，配置依赖、权限并完成 Profile 装载及首次可观察调用；只接入无关 SDK 不触发。                             |
| 开发     | 用目标版本公开入口实现 Host Tool、service/provider、Client slot、Remote 或其他插件能力；仅使用 DSH 现成功能不触发。               |
| 排错     | 定位并修复现有 DSH 插件的构建、装载、权限、调用、取消或卸载问题；模糊的“DSH 有问题”需先辨明是否涉及插件。                         |
| 升级     | 识别源版本和目标版本；当前 Skill 只能提供其锁定版本的契约，不能单靠它推断跨版本差异。审核是否及时停用不匹配的签名并寻找两端证据。 |
| 评审     | 检查现有插件的 DSH API 选型、生命周期、可靠性或性能时，应考虑本 Skill；审核或重建 Skill 产物本身属于维护任务，不触发生成 Skill。  |

从现有项目需求提取实际用户措辞和约束，不只拿表中术语拼造提示词。正向、反向和版本不符案例都要记录；通用 SDK 的认证或首次调用请求，若未指向 DSH 插件开发，不应自动纳入此 Skill。用户显式点名生成 Skill 与自动触发分别记录；元数据允许被考虑，不等于运行时一定触发。每个案例记录是否触发、何时读取哪份 reference、最终决策和任务结果；没有真实 Agent 运行时只报告预期触发范围，不宣称已验证触发率。

## 分组回报与优先级

主 Agent 只做轻量清单和任务分派，不把所有 reference 正文载入自己的上下文。按任务和相邻契约划分审核路径与文件组，每个分发 reference 只有一个主审组；在派发清单中记录相对文件路径、审核路径、对应任务、状态。跨组链接允许阅读，发现同一事实由多组维护时只报交叉关系，由主 Agent 确定权威归属。各组使用同一产物快照与精确目标版本，不从其他 tag 补事实；只读审核，不改共享文件。

子 Agent 对每个所属文件回报：相对路径、关联的任务或“暂无任务”、已检查的读取路径、适用起点及可执行状态、审核状态、证据等级、发现编号和未核查处。HOW-TO 有状态写入、异步或生命周期示例时，还要回报与链接的契约段落核对过的时序及失败分支；跨组矛盾交由主 Agent。状态只用“已审”（完成本文件适用的五维检查及上述适用核对）、“部分审核”（列出未完成维度）或“未审”；仅列出或顺带打开链接不算已审。每条发现控制为一个具体问题，采用 `[P{n}] 简短标题`，随后给出使用者目标与阻碍、精确文件/行或小节、观察和目标版本证据、**具体改进意见**（修改源文件与方法）、验证建议。冗余项说明删减或改链接后由哪里保留必要契约；证据不足时给核查建议并标“待核实”，不提出无依据的确定性删改。仅回传必要定位与结论，不粘贴整篇 reference、源码或大量无问题的段落。没有发现的文件也回报已检查范围，便于主 Agent 对账。

主 Agent 按审核路径汇总：分配文件数、已审数、部分审核数、未审数、相应文件路径与主要未审原因；逐组核对三种状态之和等于分配数。reference 各组分配数之和应等于分发 reference 总数；“入口与治理”另计根 `AGENTS.md`、分发 `SKILL.md` 与 `agents/openai.yaml` 三份，不混入 reference 分母。跨组辅助阅读不重复计数。报告中的“已审文件数”只计已审；另列部分审核与未审，避免把清单覆盖误写成内容审核完成。可用紧凑表格呈现路径和数字，文件路径较多时在表下分组列出。

- **P0**：高频或关键任务被错误指导，可能造成严重数据/权限/状态后果，或产物整体无法用于其核心目标；需有具体触发与强证据。
- **P1**：重要插件任务因错误 API、错误选型、缺少关键装载或生命周期步骤而不能正确完成。
- **P2**：任务仍可完成，但存在可复现的错误绕路、较大阅读/维护成本或某项较窄能力缺口。
- **P3**：低影响的表达、导航或重复内容；删改后关键决策和任务步骤保持正确。

不能仅凭篇幅给冗余项分级；未验证的删减收益标为假设。主 Agent 合并重复发现、核实跨组矛盾，优先亲自复查 P0/P1 的证据和最小修复归属；无法复核则标“待核实”并降低断言强度，不将子 Agent 的自报测试当作已观察结果。最终列表按 P0 至 P3 排序；同一根因影响多个文件时合并为一条，列出全部受影响位置。

## 真实任务结果

优先选有实际项目起点与可执行完成判据的任务。若做 Agent 对照，两个条件应使用同一初始快照、需求、DSH 版本、模型与工具权限；在隔离副本中运行，避免第一次改动影响第二次。比较两边的工作路径和结果，不只比较回答文字。记录使用 Skill 的触发与 reference 读取轨迹，以及未使用 Skill 时的信息来源。不能保持条件相近时，只报告观察，不作因果归因。

| 维度       | 观察和判定                                                                                            |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| 适用范围   | 相关请求是否触发目标 Skill，无关请求是否误触发；此处评估的是生成产物，审核 Skill 自身始终仅显式启动。 |
| API 准确性 | 包导出、对象成员、参数、结果、版本和可用侧是否与精确目标版本一致。                                    |
| 集成能力   | 改动是否融入项目现有初始化、配置、权限、Profile、生命周期、异步与错误处理，而非只写孤立示例。         |
| 决策能力   | 多个扩展点可选时是否选对，关键取舍是否符合任务和项目约束。                                            |
| 结果质量   | 是否遵守项目约定、构建或编译、真实装载和运行，并达到可观察的用户结果；记录失败与卸载等适用边界。      |
| 效率与边界 | 记录时间、无关文件读取、无关改动和反复试错；遇到未知 API 是否查证而非编造。                           |

区分静态阅读、声明编译、集成测试、真实运行和用户可见结果。运行任务失败时，先排除项目起点、依赖、权限或环境限制，再判断 Skill 是否导致选型、步骤或事实错误。单次对照不证明普遍增益；若多个变量不同，不声称 Skill 导致差异。

## 逐文件评估与消融

先列出分发目录的全部 reference，并把每个文件关联到独立发现的任务、产物声称的任务，或标记“暂未找到使用场景”。对相关文件记录五个问题；没有任务关联的文件先追查是否承担必要的跨任务契约，再提出冗余假设：

1. **读取时机：**`SKILL.md` 和任务路由能否在需要时指向它；无关任务会不会误读？
2. **决策价值：**它是否改变 API 选择、初始化顺序、版本判断、失败处理或清理等具体决策？
3. **准确与时效：**示例、签名和限制是否匹配精确版本及可执行证据？
4. **可用性：**Agent 能否迅速找到段落，并把规则应用于现有项目？
5. **维护成本：**是否重复其他权威段落、产生矛盾，或保存易过时而无决策价值的清单？

实际 Agent 任务优先于纯文字判断。先在完整产物中观察相关任务是否读取，以及无关任务是否误读；再选择有争议的文件或段落作消融。对照副本保持 `SKILL.md`、路由、路径和标题可用，仅移除目标文件的决策性正文，以免断链混淆结果。尽量使用相同任务和项目快照，记录 API 选择、代码与验证结果、读取量、执行步骤和时间。按“没读到、读后没找到、找到却用错、正文错误或过时”归因。任务数量依风险和证据而定；同一任务可检验多个文件。未做消融时只能提出冗余假设，不能宣称删去后不影响结果。

建议删减前说明保留的权威位置和读者从任务入口到它的路径。保留独有的公开签名、侧别、装载顺序、失败、取消、清理和验证语义。分发 Skill 离线且锁定版本；只有确认外部资料在消费环境可用、版本一致时，才考虑以外部链接替代必要正文。

### 跨文件契约与时序

对有状态写入、生成工件、Remote 往返、异步结果或资源清理的 HOW-TO，沿其显式链接和相关路由核对同一任务的前置、操作、失败与完成语义。至少选取会改变结论的状态变化，例如编辑期间远端 revision 更新、生成器没有输出、装载等待依赖、取消发生在注册之后。检查示例在变化前后捕获的值是否符合 guardrail 规定，失败后是否保留用户输入或清理 owner，以及验证步骤能否观察该分支。可用小型手工执行轨迹或隔离测试验证；只做静态推演时标明证据级别。类型检查、链接检查和代码块解析不能证明时序正确。

若 HOW-TO 与 API reference 分属不同组，各组只报告自己文件的语义和交叉引用，主 Agent 对照双方原文并裁决冲突。优先修正拥有错误事实或示例的创建素材；入口只负责及时暴露适用条件和产品限制。不要因为某条路径受阻就自行要求目标版本提供不存在的公开构建器，也不要把构建时的私有证据当作分发产物内可用资源。

## 发现记录

每条发现写为“任务与起点 → 期望行为 → 实际观察 → 产物位置和精确版本证据 → 原因分类 → 具体改进意见及源文件 → 验证方式”。分别标明已复现、静态可证、推测待验证。优先级以受阻任务的重要性、误导或错误后果、出现概率及修复成本判断，不以文字长短判断。报告还应列出各审核路径的文件计数、测试过和未覆盖的任务、候选发现来源、实际执行的命令或 Agent 运行、环境限制与结论边界。
