# 审核 DSH Plugin Development Skill

只有用户显式调用 `$review-dsh-skill` 时才启动。审核对象是本仓库已有的 `skills/dsh-plugin-development/` 及影响其创建和使用的本仓库 `AGENTS.md`；普通 DSH 开发或评审请求不自动触发。默认只读。先遵守并审核根 `AGENTS.md`，检查工作区状态、产物版本及可用的同版本 DSH checkout；生成目录不存在时说明产物审核受阻。用户指定任务或项目时优先纳入。

核心问题是：在真实插件集成任务中，该 Skill 是否帮助 Agent 更稳定、更快地交付正确结果。按[审核方法](references/review-method.md)记录任务来源、覆盖映射、执行观察和判定依据；不要用文件数、链接可达或少量案例通过来代替结果。

## 独立发现，再映射产物

先从产物外部建立插件作者的任务候选：现有消费项目的需求、代码和故障，目标版本的公开包入口、官方教程、公开调用方及真实 Profile 组合。记录每项任务的用户目标、起始项目、版本、可观察完成条件及来源；核实它能否经该版本公开入口完成。不要从产物路由、目录或旧 Skill 反推候选全集，也不要把某几个试走任务说成完整覆盖。

然后逐项映射到分发产物：Agent 何时会触发 `dsh-plugin-development`，从 `SKILL.md` 能否在需要时找到正确 HOW-TO 和 API reference，是否要猜测入口，是否有完整的项目集成步骤和验证判据。分别核对 DSH 源码内开发与独立消费项目的起点；从入口到任务步骤追踪适用环境、公开依赖、构建与装载前置，以及该路径是已验证可运行、仅契约示例还是受阻。正文写明限制而入口仍暗示可照做，也属于路由缺陷。对不可达、仅深埋于正文或没有可执行路径的任务分别记录。产物声称的任务也要纳入，但不能取代独立发现。列明检索过的来源和未核实候选；不声称穷尽所有插件任务。详见[起点与可执行状态](references/review-method.md#起点与可执行状态)。

## 分组审核 references

主 Agent 列出全部分发 reference 的路径，结合独立发现的任务按主题分组，将互不重叠的文件所有权交给多个 subagent 并行审核；例如 Host、Client、基础设施及导航。每组收到产物版本、确切文件、相关任务、所需的同版本证据与[分组回报格式](references/review-method.md#分组回报与优先级)。子 Agent 只深读所属文件；为理解链接可以查其他文件，但把跨组问题交给主 Agent，不重复裁决。主 Agent 保留任务候选与分组清单，核对每个 reference 恰好分配一次；各组逐文件回报已审、部分审核或未审状态及简短发现，不回传全文摘要。没有可用 subagent 时按限定文件批次审核，明确未覆盖范围，不声称完成全目录审核。

主 Agent 另设“入口与治理”审核路径，亲自审核分发 `SKILL.md`、`agents/openai.yaml` 和本仓库根 `AGENTS.md`：检查 frontmatter 与界面描述如何影响触发，版本边界、首屏任务链接与后续路由能否把 Agent 带到正确步骤，完成边界是否适合实现、排错和评审等不同请求，以及离线分发、生成源归属、验证与授权规则是否一致。根 `AGENTS.md` 是维护仓库规则，不随产物分发，不能把它当成消费项目自动可见的指导或 DSH API 事实。若使用真实消费项目，其 `AGENTS.md` 作为项目约束另行检查与记录，发现冲突时区分项目规则和 Skill 缺陷。详细标准见[入口与 AGENTS.md](references/review-method.md#入口与-agentsmd)。

## 检验行为与原因

在可复现的现有项目任务上，优先使用相同需求、项目起点、版本、工具和验证条件，对比“使用 Skill”与“不使用 Skill”的 Agent 行为。观察 API 选型、真实项目中的初始化/配置/权限/生命周期/异步与错误处理、编译与运行结果、无关阅读或改动、所花时间；一次对照只支持该任务的结论。不能运行真实 Agent 或目标项目时，改做明确标注的静态路径检查，不把推演写成行为验证。

各组判断所属 reference 服务哪项候选任务，或标记尚无使用场景；检查需要时是否被读取、无关任务是否误读、读后是否改善关键决策、内容是否准确且容易定位、维护成本是否合理。对高风险或疑似冗余内容，可在隔离副本中保留路径与路由，仅移除该文件的决策性内容做消融；直接删文件造成断链，不能说明内容有无价值。选择任务依据实际风险，不设每个文件固定案例数。详见[审核方法](references/review-method.md#逐文件评估与消融)。

发生失败后回查精确版本的公开类型、导出、运行时、门禁和可执行检查，区分未触发、没读到、读到但没找到、找到却用错、内容过时或错误，以及项目和环境限制。逐组检查 HOW-TO 示例与其链接的 guardrail、API reference 在状态时序、失败、取消和清理上是否一致；类型编译通过不能替代这种语义检查。跨组矛盾交给主 Agent 复核，方法见[跨文件契约与时序](references/review-method.md#跨文件契约与时序)。产物、source-map 和创建账本是线索，不能单独证明行为。无法核实则标为待核实。冗余建议必须说明删除或改为链接后，关键决策和任务步骤是否仍正确；离线产物不得默认依赖在线官方文档。

## 交付与修改边界

主 Agent 合并各组发现，复核 P0/P1、跨文件重复与冲突，按任务影响去重并确定最终优先级；subagent 的结论只是候选。报告先给任务结果及证据，再按审核路径列出分配、已审、部分审核、未审的文件数与具体文件；“入口与治理”单列根 `AGENTS.md`、分发 `SKILL.md` 与 `agents/openai.yaml`，不混入 reference 数。最后以 `[P0]` 至 `[P3]` 从高到低列发现。每条问题都必须同时给出基于证据的具体改进意见：要改哪份 `AGENTS.md`、`skill-source/`、路由、元数据或验证规则，如何改，以及怎样确认问题消除；冗余项还要说明保留内容的权威位置。优先级、计数口径和分组回报格式见[审核方法](references/review-method.md#分组回报与优先级)。分别列未测试任务、未运行检查和影响。只做审核时不修改生成产物、暂存、提交或发布；用户另行要求实施时，遵守创建 Skill 的冻结、构建、独立验证和整目录替换流程。
