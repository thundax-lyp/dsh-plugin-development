# Reference 文档模板

模板用于 `skill-source/` 中的 API reference 与 how-to。读者是制作 DSH Plugin 的开发者。标题可以按能力调整；保持各节职责，省略不适用字段时说明原因。正文只能来自目标 tag 的裁决证据，不能把模板占位语句发布为事实，也不能把 DSH 子系统说明直接换标题后当作插件开发指南。

先写清读者要完成的可观察任务，再决定 reference 的粒度。一个文件可拥有多个关系紧密的入口，但各入口的调用方式、特有前置、失败与验证不能被一段共同概述吞没。路由只指向任务步骤，事实仍由唯一 API reference 拥有；how-to 组合这些契约，不复制整篇 API 说明。

## 有限压缩与完整性

不设正文长度、文件数或代码块数量目标。路由、关键词索引和 `SKILL.md` 可以短；API reference 与 HOW-TO 按任务所需证据充分展开。压缩只用于删除重复的同一事实、无插件用途的产品内部叙述，以及已由权威 reference 自包含说明且可直接链接的契约。保留每个入口独有的公开符号与签名、对象类型及其属性、调用或注册顺序、数据形状、默认或可选挂载条件、资源 owner、取消/失败/清理、状态恢复和验证判据；某项不适用时写明原因。

合并两个入口前逐项比较插件任务、编译侧、依赖、生命周期、权限、输入输出和失败语义。只有共用完整操作路径且各自差异能在清楚的小节中说明时才合并；否则拆成相互链接的 reference。包的实现很短并不要求文档很短，包很多也不要求一包一页。尤其不能把 Client 模块装载、slot 注册、共享 UI 组件、主题样式和真实 Web 页面验证合成一句“接入 Client UI”。

审稿时从任务路由进入正文，假设读者只能使用本 Skill 与目标项目：若仍需猜测包导出、文件内容、安装方式、方法返回值、何时调用 disposer 或如何判断成功，就补足正文和 example。重复事实通过相对链接解决；链接不能指向一段同样空泛的概述。资料不足时明确写“未证实”及缺少的证据，不用概括性建议遮盖缺口。

## API reference

```markdown
# <能力与公开入口>

## 适用范围与入口

- 插件作者要完成的任务，以及何时需要此入口。
- 目标版本、公开 package/exports/符号、Host/Client/Remote 侧。
- 谁调用、实现或挂载；默认、可选或实验状态及依赖/权限前置。
- 本文的唯一契约 owner；相邻能力用相对链接。

## 契约与运行语义

- 插件如何调用、实现或注册该入口；必要的配置及真实组合路径。
- 输入、输出、事件、数据形状和约束；区分公开类型与运行时行为。直接使用的对象类型在下节逐成员展开。
- 对插件作者需要亲自编写的注册、Provider 实现、工具结果、Client slot、Remote 声明或状态 fold，给出匹配目标版本的最小完整 example，注明 Host/Client/Remote 编译面。只有无需新代码、直接按配置使用的入口可以省略代码 example，并说明具体配置与验证步骤。
- 多个合并入口逐个说明与主入口的关系和特有条件。

## 对象类型与成员

- 给出公开类型名、导入路径、适用编译侧及对象由谁创建或实现；区分配置、输入、结果、事件 payload、服务接口和句柄。
- 对插件作者会构造、读取或实现的每个未废弃属性，写明准确类型、必填/可选、允许值或判别条件、默认值由谁设置、语义及约束。嵌套对象、联合分支和回调参数按任务实际访问的层级展开，不用一个笼统的 `object` 或 `Record<string, unknown>` 代替已公开的结构。
- 对方法写参数和返回值类型、同步/异步与错误通道；对事件写触发时机、payload、顺序或重放边界；对返回句柄写 owner、disposer、取消和关闭时机。无默认值或运行时未保证的字段明确说明，不从可选类型猜默认行为。
- 只收录目标 tag 中仍可用于新插件的成员；被明确标为待废弃的类型或成员按下文的废弃筛选规则排除。

## 生命周期与状态

- 注册/创建、资源 owner、取消、释放、卸载和恢复。
- 持久事实与临时通知；状态从哪里重建。

## 失败、权限与边界

- 可观察错误、部分成功、重试或回滚、权限和挂载条件。
- 未实现、内部、实验或需要外部协议的行为明确标注。

## 验证

- 目标 tag 的类型/实现/gate/测试证据见 source-map；列出针对使用者任务的验证路径。
- 说明静态检查、示例编译和行为测试各自能证明什么，未验证的路径保持未验证。
```

正文中不要重复一份庞大 source-map；精确证据路径集中在 `maintenance/source-map.md`，claim 保留机器可核查的 owner。不要把包清单描述直接改写为运行时保证。若一段内容无法回答插件作者“何时使用、如何接入、怎样验证”，将其移到证据账本或删去。

### 成员表的呈现方式

按对象分别列出成员；表格只是阅读格式，不能替代语义核查：

| 成员                  | 公开类型     | 必填与默认                  | 语义和约束                 | 生命周期或失败边界        |
| --------------------- | ------------ | --------------------------- | -------------------------- | ------------------------- |
| 从目标 tag 核实的属性 | 精确声明类型 | 必填/可选，默认来源或无保证 | 合法值、判别条件、读写规则 | owner、错误、清理或不适用 |

对象有多个联合分支时先说明判别字段，再分别列各分支的特有成员。方法、事件和回调可以另用签名表或小节，以免把参数、结果与事件 payload 混成同一种“属性”。不得复制整份声明文件来充数；只展开插件任务需要使用的公开成员，并保持相邻链接可追溯到完整 owner。

## 废弃筛选

在精确目标 tag 的公开代码中核对弃用状态，再依次检查声明或实现旁的 JSDoc、生成声明中的注释及所属包文档里的 `@deprecated`、明确的“待废弃”或等价标记，并回看其标注范围及推荐替代入口。标记加在类型、函数或入口上时，不把该入口写入普通任务路由、API 指导或 example；只标记某个属性、方法、事件或参数时，保留可用的父对象，排除被标记成员。注释或文档的标记与代码实际公开性或行为冲突时，按代码优先裁决并记录冲突；不要因为代码中提到“deprecated HTML/DOM API”就误判整个 DSH 类型为待废弃。

排除项仍在 `coverage.json` 或 `claims.json` 的裁决记录中写明符号、标记来源、目标 tag 证据和替代入口（若已核实）；这份维护账本不属于面向开发者的常规 reference。不能凭旧版本、孤立注释或一个模糊的文档措辞隐藏仍受支持的入口。

## Example 编写契约

Example 是从读者任务出发的可执行切片，不是孤立的 API 调用片段。根据任务选最小范围，完整交代以下各项；不适用时简短说明原因：

1. **前置与位置：**目标 tag、插件所在侧、依赖的公开包与导出、服务注入或 Profile 条件。独立消费包与上游 monorepo 内包分开写，不能把 `workspace:^`、上游相对 `tsconfig` 或内部路径当作可直接安装的外部模板。
2. **组成文件：**入口代码及所需 `package.json`、Config/schema、Client export、Remote 声明、bundle/patch 或生成步骤。每个文件标出路径和执行顺序；省去某文件时，读者仍应能确定由谁提供它。
3. **运行契约：**真实输入、规范结果、模型可见内容和 UI 展示分别如何产生；资源 owner、取消信号、失败或部分成功、卸载与跨重启事实如何处理。不要用 `any`、伪造的返回值、忽略诊断或未声明的全局能力掩盖契约缺口。
4. **装载与观察：**怎样通过目标版本公开入口把包选入真实 Profile，怎样确认依赖和插件 fiber 已激活，以及成功、拒绝/失败、取消、卸载、重连或恢复中哪些情形适用。
5. **验证证据：**给出在精确 checkout 或独立消费项目中实际可运行的命令、断言或手工观察步骤；区分声明编译、真实 Loader 组合、行为和用户可见结果。没有运行的步骤写作待验证，不得以源码路径存在或示例编译通过宣称已装载。

代码块使用目标 tag 公开类型可编译的完整最小骨架；Host 与 Client 分开编译，Remote 先运行目标版本生成器再核对两侧类型。展示代码时只包含当前任务必需的语句，重复的 API 定义通过相对链接指向权威 reference。若上游只有内部样例，应先找到可供外部插件使用的公开入口；找不到时明确写出不可直接完成的边界，而不是将内部样例改名后发布。

最终 reference 中，一个涉及代码的 example 宜按下面的阅读顺序呈现；文件名和步骤由目标 tag 的真实契约决定，这不是可直接复制的 DSH API：

```text
目标及前置 → 文件清单与依赖 → 各文件完整内容 → 构建与安装 → Profile 挂载 →
一次成功调用 → 失败/取消检查 → 卸载或恢复检查 → 已运行与未运行的验证
```

例如“为插件注册模型工具”的 example 至少要让读者找到工具所在包的 manifest 与入口、参数和输出 schema、`execute` 与规范结果、模型可见渲染、注册所在的插件 scope、权限与取消处理、Profile 装载路径，以及一次调用和卸载后的断言。“在 Web slot 显示结果”的 example 则必须同时交代 Host 行、`./client` 导出、Client 注册、所消费的持久结果、重连和卸载；仅展示一个浏览器事件监听器不足以证明 slot 集成。上述是内容核对清单，不是可以直接发布的 API 声明或固定版本示例。

## How-to

以目标版本文档中的“如何……”及等价开发问题、公开调用方和真实组合为任务线索；先裁决插件作者能否经公开入口实现，再写业务结果和完整操作路径。一个业务能力若依赖多个 API 对象，HOW-TO 负责说明这些对象如何按顺序协作、数据如何在其间流转、由谁装载和清理，以及何时算完成；各对象的属性与方法定义仍由各自的权威 API reference 拥有。

```markdown
# <可完成的插件任务>

## 目标与前置

- 用户要完成的结果、目标版本、所需公开入口、依赖与挂载条件。
- 链接权威 API reference；只摘任务需要的约束。

## 实现步骤

1. 列出任务所需文件和依赖，创建最小完整包或插件骨架，声明 Host/Client/Remote 所在侧。
2. 按实际依赖和调用顺序组合所需 API 对象与配置，说明数据如何跨对象及 Host/Client/Remote 侧流转；用符合上文 Example 编写契约的代码注册入口、处理输入输出，并明确资源所有权。
3. 处理失败、取消、清理及可恢复状态；说明尚无可恢复事实的任务为何不需要持久记录。
4. 经公开安装/装载入口接入真实 Profile 或调用路径，写出成功时可观察的结果。

## 验证与完成边界

- 列出本任务实际可运行的类型、生成、门禁、测试或手动验证命令。
- 给出成功、失败、取消、卸载等适用情形的判据，并说明未覆盖的运行路径。
```

How-to 展示端到端操作，不重复或改写 API 契约。示例必须与目标 tag 的公开类型、包导出和运行时一致；不能用 `any`、忽略诊断或虚构 API 掩盖缺口。只写“使用插件管理入口安装”“在目标 Profile 验证”而没有可执行步骤与判据，不算完成 HOW-TO。
