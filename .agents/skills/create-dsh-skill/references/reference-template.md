# Reference 文档模板

模板用于 `skill-source/` 中的 API reference 与 how-to。读者是制作 DSH Plugin 的开发者。标题可以按能力调整；保持各节职责，省略不适用字段时说明原因。正文只能来自目标 tag 的裁决证据，不能把模板占位语句发布为事实，也不能把 DSH 子系统说明直接换标题后当作插件开发指南。

正文中的段落、列表、表格说明、示例讲解和代码注释使用中文；标题可以使用英文。公开符号、类型、包名、命令、路径、协议字段及代码字面量保持原样，必要的英文检索关键词可以保留。不要因目标版本的来源文档是英文，就直接复制英文叙述到分发 reference。

先写清读者要完成的可观察任务，再决定 reference 的粒度。一个文件可拥有多个关系紧密的入口，但各入口的调用方式、特有前置、失败与验证不能被一段共同概述吞没。入口任务表指向 HOW-TO 中的任务步骤；对象事实由唯一 API reference 拥有，HOW-TO 从这些事实说明如何完成任务，不复制整篇 API 说明。

## 有限压缩与完整性

不设正文长度、文件数或代码块数量目标。主题页和 `SKILL.md` 中的各索引可以短；API reference 与 HOW-TO 按任务所需证据充分展开。压缩只用于删除重复的同一事实、无插件用途的产品内部叙述，以及已由权威 reference 自包含说明且可直接链接的契约。保留每个入口独有的公开符号与签名、对象类型及其属性、调用或注册顺序、数据形状、默认或可选挂载条件、资源 owner、取消/失败/清理、状态恢复和验证判据；某项不适用时写明原因。

合并两个入口前逐项比较插件任务、编译侧、依赖、生命周期、权限、输入输出和失败语义。只有共用完整操作路径且各自差异能在清楚的小节中说明时才合并；否则拆成相互链接的 reference。包的实现很短并不要求文档很短，包很多也不要求一包一页。尤其不能把 Client 模块装载、slot 注册、共享 UI 组件、主题样式和真实 Web 页面验证合成一句“接入 Client UI”。

审稿时从产物 `SKILL.md` 的任务表，或经对象名称与 `references/object-index.md` 进入正文，假设读者只能使用本 Skill 与目标项目：若仍需猜测包导出、文件内容、安装方式、方法返回值、何时调用 disposer 或如何判断成功，就补足正文和 example。重复事实通过相对链接解决；链接不能指向一段同样空泛的概述。资料不足时明确写“未证实”及缺少的证据，不用概括性建议遮盖缺口。

## 插件形态总览

产物 `SKILL.md` 在任务表前给出目标版本的插件产品形态表。形态是读者选择“做什么、在哪里被使用”的入口；function/object/class 是模块写法，Host/Client/Remote 是运行侧或组合边界，均不能直接充当形态清单。按[入口范围](entrypoint-scope.md#插件产品形态盘点)逐类裁决数量与名称；同一插件可同时提供多类能力。每行用简短中文回答：

| 形态                | 提供的能力         | 呈现或发现位置                                                         | 如何装载与使用                                           | 实现指南         |
| ------------------- | ------------------ | ---------------------------------------------------------------------- | -------------------------------------------------------- | ---------------- |
| 目标 tag 核实的形态 | 插件作者交付的结果 | Agent、Web、其他插件或外部调用方能观察到什么；无独立 UI 时说明观察路径 | 所需公开入口、Profile/配置前置，以及用户或调用方怎样触发 | 对应 HOW-TO 链接 |

表格只负责选型和导航，不抄 API 成员或完整操作步骤。不能只列 Tool 而遗漏已核实的 Service/Provider、Client UI 或其他形态；也不能把候选线索写成已发布能力。每个形态至少能从该表到达一条完整 HOW-TO，并由该任务进一步到达权威 API 契约。呈现与使用须分别核查：服务型插件可能没有单独界面，工具可由模型调用但结果如何显示另有渲染契约，Client UI 要指明实际可到达的页面或 slot。没有公开装载或可观察使用证据时写出边界，不以源码中有组件或类型推定可用产品形态。

## API reference 的主题与子主题

按插件作者的使用路径分层，不按包名或行数机械切割。一个主题页解释对象关系、适用场景、选型、共同装载顺序和跨对象边界；它须链接本主题的每个子主题页，不能只是一张文件目录。一个子主题页容纳关系紧密且可一起理解的对象，每个纳入对象有独占、带公开符号名的二级或更深标题；对象的具体契约、成员、生命周期、失败及帮助理解契约的最小片段只在这里维护。子主题页要能从对象索引直接进入并独立读懂，不依赖先读另一篇正文才能理解签名和前置。无需每个对象一个文件，也不设页数或行数上限；当编译侧、装载条件、生命周期或失败语义不同，或单页已难以按对象定位时，再拆成不同子主题。

主题页与子主题页都在 manifest 中使用 `kind: "api-guardrail"`，新目标分别标 `role: "topic"` 和 `role: "subject"`；两者都标所属 `topic`，子主题另标唯一 `subject`。`api-surface.json` 的纳入对象只能把子主题页的小节作为唯一 `owner`。`coverage.json`、`claims.json` 与 source-map 随事实归属指向对应页；主题页只拥有关系和选型事实，不重复对象成员。HOW-TO 拥有单对象及跨对象任务的操作步骤，引用各对象的权威子主题页；较长的端到端 example 由 HOW-TO 导航到独立文件。

主题页结构：

```markdown
# <主题与插件用途>

## 对象关系

- 本主题有哪些对象，各自由谁创建、实现或调用，如何传递数据或共享生命周期。
- 说明 Host/Client/Remote 侧和默认、可选或实验组合的边界。

## 选型与使用

- 按插件任务说明何时选哪个对象、需要哪些公开包和装载前置，以及对象间的依赖顺序。
- 链接本主题每个子主题页；具体任务的完整实现链接对应 HOW-TO。
```

子主题中每个对象小节至少回答：

- **入口与适用性：**公开类型名、导入路径、目标版本、编译侧、对象由谁创建或实现、默认或可选挂载、权限和配置前置。
- **成员与运行语义：**插件会构造、读取或实现的属性、方法、事件、回调、嵌套结构和联合分支；写明精确类型、必填和默认来源、输入输出、错误通道及运行时约束。
- **生命周期与状态：**注册、资源 owner、取消、释放、卸载、持久事实和恢复路径；不适用的项说明原因。
- **失败与验证：**可观察错误、部分成功、重试或回滚边界，及目标版本可执行的类型、装载和行为验证。
- **对象级说明：**给出理解成员约束所必需的最小调用片段或配置形状，并链接使用该对象的 HOW-TO。任务操作、装载、观察与业务验证归 HOW-TO；较长的完整代码归其链接的 example。若 API 页已有经核实的完整用法，HOW-TO 链接该段并补足任务目标、缺失步骤和完成判据，不重抄原文。

正文中不要重复一份庞大 source-map；精确证据路径集中在 `maintenance/source-map.md`，claim 保留机器可核查的 owner。不要把包清单描述直接改写为运行时保证。若一段内容无法回答插件作者“何时使用、如何接入、怎样验证”，将其移到证据账本或删去。

### 成员表的呈现方式

按对象分别列出成员；表格只是阅读格式，不能替代语义核查：

| 成员                  | 公开类型     | 必填与默认                  | 语义和约束                 | 生命周期或失败边界        |
| --------------------- | ------------ | --------------------------- | -------------------------- | ------------------------- |
| 从目标 tag 核实的属性 | 精确声明类型 | 必填/可选，默认来源或无保证 | 合法值、判别条件、读写规则 | owner、错误、清理或不适用 |

对象有多个联合分支时先说明判别字段，再分别列各分支的特有成员。方法、事件和回调可以另用签名表或小节，以免把参数、结果与事件 payload 混成同一种“属性”。不得复制整份声明文件来充数；只展开插件任务需要使用的公开成员，并保持相邻链接可追溯到完整 owner。

## 废弃筛选

在精确目标 tag 的公开代码中核对弃用状态，再依次检查声明或实现旁的 JSDoc、生成声明中的注释及所属包文档里的 `@deprecated`、明确的“待废弃”或等价标记，并回看其标注范围及推荐替代入口。标记加在类型、函数或入口上时，不把该入口写入入口任务表、对象索引、API 指导或 example；只标记某个属性、方法、事件或参数时，保留可用的父对象，排除被标记成员。注释或文档的标记与代码实际公开性或行为冲突时，按代码优先裁决并记录冲突；不要因为代码中提到“deprecated HTML/DOM API”就误判整个 DSH 类型为待废弃。

排除项仍在 `coverage.json` 或 `claims.json` 的裁决记录中写明符号、标记来源、目标 tag 证据和替代入口（若已核实）；这份维护账本不属于面向开发者的常规 reference。不能凭旧版本、孤立注释或一个模糊的文档措辞隐藏仍受支持的入口。

## Example 编写契约

Example 是从读者任务出发的可执行切片，不是孤立的 API 调用片段。根据任务选最小范围，完整交代以下各项；不适用时简短说明原因：

1. **前置与位置：**目标 tag、插件所在侧、依赖的公开包与导出、服务注入或 Profile 条件。独立消费包与上游 monorepo 内包分开写，不能把 `workspace:^`、上游相对 `tsconfig` 或内部路径当作可直接安装的外部模板。
2. **组成文件：**入口代码及所需 `package.json`、Config/schema、Client export、Remote 声明、bundle/patch 或生成步骤。每个文件标出路径和执行顺序；省去某文件时，读者仍应能确定由谁提供它。
3. **运行契约：**真实输入、规范结果、模型可见内容和 UI 展示分别如何产生；资源 owner、取消信号、失败或部分成功、卸载与跨重启事实如何处理。不要用 `any`、伪造的返回值、忽略诊断或未声明的全局能力掩盖契约缺口。
4. **装载与观察：**怎样通过目标版本公开入口把包选入真实 Profile，怎样确认依赖和插件 fiber 已激活，以及成功、拒绝/失败、取消、卸载、重连或恢复中哪些情形适用。
5. **验证方法：**给出在精确 checkout 或独立消费项目中可执行的命令、断言或手工观察步骤；分别说明声明编译、真实 Loader 组合、行为和用户可见结果的判据。执行记录与未运行项写入创建报告，不写进分发 example；不得以源码路径存在或示例编译通过宣称已装载。

代码块使用目标 tag 公开类型可编译的完整最小骨架；Host 与 Client 分开编译，Remote 先运行目标版本生成器再核对两侧类型。展示代码时只包含当前任务必需的语句，重复的 API 定义通过相对链接指向权威 reference。若上游只有内部样例，应先找到可供外部插件使用的公开入口；找不到时明确写出不可直接完成的边界，而不是将内部样例改名后发布。

完整代码占用较多篇幅时，另建 `skill-source/examples/example-<任务名>.md`，在 manifest 中以 `kind: "example"` 输出为 `references/<side>/examples/example-<任务名>.md`。同一任务有独立的 Host、Client 或 Remote 实现时，可在任务名后加运行侧分别建文件。HOW-TO 在需要创建文件的步骤处链接相应 example；它保留目标、前置、操作顺序、关键选择、失败处理和完成判据，只保留解释关键决策所需的短代码片段。example 则集中放文件清单、各文件完整代码、构建、装载和相应验证操作。API 页仍拥有对象关系与权威契约，example 用相对链接引用，不复制成员表。

示例文件放在 `references/<side>/examples/`，示例检查器递归读取其中的 Markdown 代码块；不要为缩短 HOW-TO 将代码移到未纳入检查的孤立附件。一个 example 可以被相关任务复用，但每个 example 都须从至少一个具体 HOW-TO 任务小节直接到达。纯配置任务若步骤已经完整，不为满足文件形式而增加空 example。独立文件让读者按需打开代码，不降低完整性：HOW-TO 的步骤、example 的文件内容和验证判据合起来仍须足以完成任务。

涉及代码的 example 文件宜按下面的阅读顺序呈现；文件名和步骤由目标 tag 的真实契约决定，这不是可直接复制的 DSH API：

```text
目标及前置 → 文件清单与依赖 → 各文件完整内容 → 构建与安装 → Profile 挂载 →
一次成功调用 → 失败/取消检查 → 卸载或恢复检查 → 可执行的验证方法与判据
```

例如“为插件注册模型工具”的 example 至少要让读者找到工具所在包的 manifest 与入口、参数和输出 schema、`execute` 与规范结果、模型可见渲染、注册所在的插件 scope、权限与取消处理、Profile 装载路径，以及一次调用和卸载后的断言。“在 Web slot 显示结果”的 example 则必须同时交代 Host 行、`./client` 导出、Client 注册、所消费的持久结果、重连和卸载；仅展示一个浏览器事件监听器不足以证明 slot 集成。上述是内容核对清单，不是可以直接发布的 API 声明或固定版本示例。

## How-to

以目标版本文档中的“如何……”及等价开发问题、公开调用方和真实组合为任务线索；先裁决插件作者能否经公开入口实现，再写业务结果和完整操作路径。单对象任务也需要 HOW-TO 说明如何编写、装载、调用、处理失败并验证；多对象任务还要说明对象协作、数据流转和所有权。各对象的属性与方法定义仍由权威 API reference 拥有。

HOW-TO 的文件数按互不重叠的任务边界决定，不设数量上限，也不因任务只涉及一个对象而合并。不同结果、前置条件、运行侧、装载方式或失败恢复路径需要独立理解时可拆成多篇；多个任务确实共用完整操作路径时可放在同一篇的独占小节。先从 API 子主题确认可用对象和约束，再将“如何使用”写入对应 HOW-TO。若 API 页已经完整说明同一操作，HOW-TO 可以缩短重复步骤并精确链接原段，但仍须交代本任务的目标、缺失的操作环节和完成判据；不得用一个泛化入口替代多个不同任务。

```markdown
# <共同主题或插件用途>

## <本任务的可观察结果>

### 目标与前置

- 用户要完成的结果、目标版本、所需公开入口、依赖与挂载条件。
- 链接权威 API reference；只摘任务需要的约束。

### 实现步骤

1. 列出任务所需文件和依赖，声明 Host/Client/Remote 所在侧；需要完整代码时，直接链接对应的 `example-*.md`，让读者按需查看最小完整包。
2. 按实际依赖和调用顺序组合所需 API 对象与配置，说明数据如何跨对象及 Host/Client/Remote 侧流转；在步骤中解释注册、输入输出和资源所有权，完整代码交给 example。
3. 处理失败、取消、清理及可恢复状态；说明尚无可恢复事实的任务为何不需要持久记录。
4. 经公开安装/装载入口接入真实 Profile 或调用路径，写出成功时可观察的结果。

### 验证与完成边界

- 列出本任务实际可运行的类型、生成、门禁、测试或手动验证命令。
- 给出成功、失败、取消、卸载等适用情形的判据；目标版本确实不支持的路径写明产品边界。
```

How-to 展示端到端操作，不重复或改写 API 契约，也不把整套多文件代码埋在步骤中。链接出去的 example 必须与目标 tag 的公开类型、包导出和运行时一致；不能用 `any`、忽略诊断或虚构 API 掩盖缺口。只写“使用插件管理入口安装”“在目标 Profile 验证”而没有可执行步骤与判据，不算完成 HOW-TO。
