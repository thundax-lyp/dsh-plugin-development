# SDK 子进程入口与 JSON-RPC 服务

## 适用范围与入口

目标 `dsh-v0.2.0-rc.1`。`@deepseek-ai/dsh-sdk-client` 是运行在 Harness 外部的 TypeScript 库，并非 Cordis 插件。它启动同版本 `dsh --profile sdk` 子进程；该 Profile 中 `@deepseek-ai/dsh-sdk-jsonrpc-server` 作为 Cordis 插件提供 stdio JSON-RPC。`@deepseek-ai/dsh-sdk-protocol` 导出两端共享的传输及请求、通知类型。外部调用方的完整骨架见[从 TypeScript 驱动 SDK Profile](how-to-run-sdk-profile.md)。

## 公开契约

| 入口              | 插件作者可用成员                                                                                                                                                                         |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DeepSeekHarness` | `new (DeepSeekHarnessOptions)`、`start()`、`session(id?)`、`run(input, options?)`、`client`、幂等终结性 `close()`、`Symbol.asyncDispose`。首次使用才 spawn；一个实例可持有多个 Session。 |
| `HarnessSession`  | `id`、`harness`、`run(input,{onNotification?})`。等待提交的入队回执，然后收集到整个 agent 下一次 `idle`。                                                                                |

| `RunResult`       | `sessionId`、`finalResponse`、根 Session 的 `events`、会话树的 `notifications`。`finalResponse` 来自活动区间最后一条已提交 assistant 文本，不能推断它只由本次 prompt 导致。              |
| 协议              | `initialize`、`session/prompt`、`shutdown` 请求；`session.event`、`session.status`、`subagent.started`、`subagent.finished` 通知。后两者仅报告进程内子代。                               |

`DeepSeekHarnessOptions` 包括 `dshBin`、`profile`（默认 `sdk`）、有序 `patches`、`dshHome`、`processCwd`、子进程完整 `env`、请求/初始化/关闭超时，以及 Session `cwd`、provider、model、reasoningEffort、maxTokens。`cwd` 在握手前变成绝对路径；子进程环境若显式给出，会**整体替换**父环境，凭据传递由调用方负责。默认 provider/model 是 `deepseek-official`/`deepseek-v4-flash`；服务端在 `initialize` 校验实际 adapter 路由和正整数 maxTokens。

**精确 API 对象与成员**

`@deepseek-ai/dsh-sdk-protocol` 的 `JsonRpcLineTransport` 使用调用方持有的 `Readable`/`Writable` 字节流的低层传输：调用方先 `start()` 附加读监听，结束时 `close()` 移除监听并拒绝在途请求，但它不销毁调用方的流。`request(method, params, signal?)` 的取消只移除本地等待，不代表服务端工作被取消；`notify` 单向发帧，`onRequest`/`onNotification` 替换处理器，`flush()` 等待既有帧的写回调。若使用现成 `HarnessClient`，进程、流和关闭阶梯由客户端管理，无需另建传输。协议错误 `JsonRpcResponseError` 保留数字 `code` 与可选 `data`；写失败/关闭可抛普通 `Error`。下面的类型是线格式契约，应用不应把类型检查当作服务端鉴权或模型响应证明。

## 生命周期、失败与边界

客户端从 durable `agent/inbox/spliced` 回执确认本次消息进入 Session，然后将已提交 `session.event` 放入结果。`onNotification` 在 wire 顺序调用；高层 `run` 结束时释放临时订阅。中途无逐 prompt 取消方法；调用方结束运行需关闭整个 Harness。`close` 先请求 `shutdown`，再经过 stdin EOF、SIGTERM、SIGKILL 阶梯并等待进程退出。握手失败且清理成功可用新进程重试；清理也失败时保留两个原因并避免并行 spawn。`JsonRpcResponseError`、`RequestTimeoutError`、`SdkProtocolError`、`TransportClosedError` 分别表示协议拒绝、时限、非法响应、传输终止。

服务插件由 Profile 装载，初始化前等待 Loader 当前树 settled；关闭时先 flush 响应，再 dispose 根 fiber，最后退出。模型可见工具、权限、Session 持久性来自所选 Profile，并非 SDK 客户端自动提供。实际模型调用需要可用的 provider 认证；静态类型或脚本化协议测试不证明 provider 行为。

## 验证

在目标版本声明下编译消费代码；用真实 `dsh --profile sdk` 或只实现协议的隔离子进程验证握手、通知、返回与 close。后者只证明 SDK 协议边界。再用目标 Profile 验证 adapter/权限/Session 持久化与关闭排空，失败和取消分别验收。
