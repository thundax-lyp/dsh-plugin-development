## Source/runtime adjudication

- `WebServer` matches exact first, then longest prefix; fallback is one seat. Duplicate named routes, upgrade paths, and fallback throw. It does not authenticate, authorize, serve files or implement TLS. Raw route handlers own method/body/response. `Service.init` binds immediately; its dispose closes HTTP and tracked upgraded sockets. Source and tests: `packages/host/webserver/src/index.ts`, `tests/webserver.spec.ts`.
- Host Connection requires credentials. When WebServer exists it registers its own `/api` prefix through `ctx.inject(['webServer'])`; that bridge calls `connection.admit` before request waterfall/body bridging. `admit` returns operator Peer or 401/403. Browser auth uses a process launch token for initial index exchange and signed authority scoped cookie stored through the credential provider. Host/Origin trust logic is independent from authentication. Source and tests: `packages/client/connection/src/{index,rpc-host,browser-auth,api-request-trust}.ts`, `tests/{node-half.host,browser-auth,api-request-trust}.spec.ts`.
- Connection Fetch route registration is exact below `/api`, with body mode and methods. A registration is fiber scoped; current in-flight requests continue after withdrawal. RPC `handle` occupies a non-`/api` channel, `intercept` one shared `/api` seat. Client `/client` has HTTP unary caller and service generation/state observers; Gateway owns ordinary served browser generation source and stream carrier. Source/tests: `packages/client/connection/src/{rpc,rpc-host,client/index,client/rpc,client/connection}.ts`, `tests/{node-half.host,client-apply.client}.spec.ts`.
- Formal Web composition: `packages/bundle/web-app/cordis.patch.yml` mounts `webserver`, `web-runtime`, and `connection` rows. The Connection row gets `trustedHosts` from `webRuntime`; this is a Profile composition fact, not something every custom profile receives automatically.

## Independent consumer validation actually run

Fixture: `evidence/tests/web-ingress-consumer/`; fresh npm install against published `@deepseek-ai/cordis@4.0.4`, `@deepseek-ai/dsh-host-webserver@0.2.0-rc.1`, `@deepseek-ai/dsh-client-connection@0.2.0-rc.1`, TypeScript 6.0.3. `npm run build` passed Host declaration compilation. `npm pack --dry-run --json` passed, listing `lib/index.js`, `lib/index.d.ts`, `cordis.patch.yml`, `package.json`. `npm run smoke` started the actual published WebServer and Connection on loopback/OS port, with a process-local credential-record double, then mounted the example plugin in a Cordis context. Responses observed: 401 without a cookie; initial `authenticatedUrl` request returned 303 and signed cookie; that cookie yielded 200 JSON, admitted POST yielded 405, explicit cross-site and Origin-mismatch requests yielded 403, and a raw HTTP request with untrusted Host yielded 403. After plugin fiber disposal, authenticated `/probe` returned 404. An initial attempt to override Host using fetch yielded 200 because that carrier supplied the URL authority; the final fixture used `node:http.request` for the Host test and passed.

The credential record store is only a process-local test double; these runs do **not** validate credential persistence, a real browser, Web Profile Loader installation, Client generation recovery, LAN binding, upgrade or streaming. The Host/Origin fence was exercised on separate Host mismatch, Origin mismatch, and `sec-fetch-site: cross-site` requests. No source checkout monorepo test/build was run because its `node_modules` is absent and those tests require its build prerequisites. Profile scenarios remain explicit follow-up validation, not completion claims.
