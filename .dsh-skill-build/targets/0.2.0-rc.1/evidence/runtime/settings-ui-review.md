## Source adjudication

- Settings Client service `ctx.configForms` is supplied only when `remote` and `remote.settings` exist. Its shared describe mirror reloads on settings document changes and `connection/reset`; non-loopback Host persistence is disabled by its own `remote.$host.isLoopback` choice. `get(entryId)` uses the Host Profile entry id as namespace. `whileServed` owns no caller fiber effect, so consumer wraps its disposer in `ctx.effect`.
- `SettingsFormModel` stages edits and sends one revision-fenced namespace mutation on save, then separately sends each nonblank write-only secret. Partial success across settings and credential writes is possible. Discard removes drafts; model disposal removes scope subscription; `SettingsForm` calls discard on component unmount. The read-only banner comes from `SettingsForm`, while its Save disabled predicate itself omits `writable`; the model rejects save when `writable=false`, so browser presentation still deserves verification.
- `plugins.row.config` is a keyed root slot, key `<package>#<row id>`, receiving `view: 'summary'|'page'` and an optional Host-owned `form`. `plugins.item` is for official standalone items, not ordinary third-party bundle rows. Shipped shell settings companion package uses an official `plugins.item` example because it edits a built-in namespace.
- Client module system scans enabled bare package Loader rows for `dsh.client`, obtains built `./client`, and expects a lazy CommonJS factory registration. The upstream build helper `packages/client/tsdown.client.ts` is repository-local, not a published package export. The fixture's custom esbuild wrapper is deliberately limited to one entry, no CSS or async chunk, only platform module `require`s.
- Shipped permission UI package has an empty Host root `apply` and a `./client` implementation. It registers General future-session default and current-session chooser separately; default writes `permission.defaultPreset` through revision-fenced settings mutation, current session uses `/permission <preset>` through live Session command. Catalog read is generation fenced and invalidated on Host notification/reconnect. Code/runtime tests exist in `packages/client/ui-permission-presets/tests`, but were not run here.

## Independent validation actually run

Fixture `evidence/tests/settings-card-consumer/` uses npm published rc.1 packages, TypeScript 6.0.3 and esbuild. First dependency install failed because the draft had a nonexistent `@deepseek-ai/schemastery@0.5.4`; exact checkout declares published `3.18.4`, corrected in fixture/HOW-TO. A second install succeeded. Initial compile failed because a `loader/volatile-update` handler did not import its event declaration; the minimal Host example was narrowed to initial log and operation-time `.get()` guidance. Final `npm run build` passed Host and Client declaration compilation and emitted `lib/client.js`. `npm run verify:client` executed the bundle registration in an isolated VM and observed matching id, factory export, `inject=['slots','configForms']`, and only three platform requests (`react`, `react/jsx-runtime`, `@deepseek-ai/dsh-client-ui-primitives`). `npm pack --dry-run --json` listed the Host and Client JS/declarations, manifest and patch. A direct published `Config({})` check observed `config.endpoint.get() === 'https://example.invalid'`.

The VM did not call Client `apply`, render React, run the real Loader/client-modules, or save against a Host Profile. The fixture package's credential and server surfaces are not exercised. Real Web Profile module loading, slot visibility, write/revision persistence, CSS/keyboard behavior and permission UI are still unverified. No monorepo tests were run; target checkout has no installed dependencies.
