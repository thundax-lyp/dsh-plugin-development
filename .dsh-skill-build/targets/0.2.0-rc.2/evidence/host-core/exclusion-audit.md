# Host/Core exclusion audit — `dsh-v0.2.0-rc.2`

Read-only recommendations against `639ed015397290b3745d163aafe02ffee4aa3f84`. This file proposes ledger changes; it does not alter `coverage.json` or `api-surface.json`. The current Host HOW-TO calls several public entries or members that the ledgers mark excluded. A claim that a package is "covered under its canonical subsystem" is a reason to **merge it into that subsystem**, with an exact owner section and a concrete relationship, when the plugin task actually mounts or calls it. It is not, by itself, an exclusion reason.

## Exclusions that can remain, with specific rationale

- `cap-044` (`agent-loop-testkit`), `cap-208` (`llm-mock-server`), `cap-210` (`llm-replay`), and `cap-263` (`session-snapshot`) can remain excluded from normal plugin instructions when used only by target repository tests. Cite their test-only package role and any runtime export check rather than a generic "not selected" reason.
- `cap-250`–`cap-253` (`session-format-vN-to-vN`) can remain excluded: `packages/session/session-format-catalog` selects these historical migration implementations on restore; a new plugin must not call them as its write format. The catalog/backend boundary still needs a concrete restore task if mentioned.
- `export:@deepseek-ai/dsh-subagent:./internal` can remain excluded despite a published subpath: it is explicitly an internal namespace, and ordinary provider/child tasks use the root and supported Client/Remote entries. Do not treat publication alone as plugin support.

These are source-level proposals. They do not prove that a consumer package resolves, a Profile activates, or any restart/Remote behavior works. Ledger changes should be followed by a section-level reference check and the exact-checkout compilation and scenario gates.
