# Infra task-critical reference gaps (0.2.0-rc.2)

Scope: the 25 covered task paths, especially `infra-resource-seams-and-providers`. The reference gaps below have been filled in this agent's three assigned Infra source pages; shared API ledgers remain for the main agent to reconcile. An `included` object in `reconciliation.json` denotes a request/result type, implemented provider interface, or operation the selected task actually uses. Type aliases that the compiler alone infers and helpers owned by another task were excluded or merged.

The “current surface” comparisons in the audit table describe the state when these gaps were found, before the accompanying source-page edits.

No newly identified absence of a published public entrypoint blocks these eight task contracts. The Client/Web Remote example still needs a consumer-owned lazy-CJS Client bundle build and real Profile verification, as already stated in `skill-source/how-to/client-web.md`.

## Direct member disposition proposal

The eight contracts are now described under the existing Infrastructure provider call shapes anchor and its new subsections. For the shared `api-surface.json`, include the following *direct members of included objects* when the member ledger represents them. A nested request/result type remains an included object with its task-critical fields described in that object's reference; do not manufacture a direct member on a different owner.

| Included owner | Direct members to include | Task reason |
| --- | --- | --- |
| `AttachmentStore` | `saveFile`, `saveFileStream`, `readFileStream`, plus existing `saveImage`, `saveImages`, `readImage` | File-capable provider implementation and stream readback are selected task operations; defaults explicitly reject unsupported files. |
| `CredentialProvider` | `describe`, `unset`, `readRecord`, `describeRecord`, `listRecords`, `modifyRecord`, `deleteRecord`, plus existing `resolve`, `set` | A selected provider must implement both reference and record halves, including serialized mutation. |
| `AuthorizationService` | `registerFlow`, `begin`, `cancel`, `list` | The author registers a flow and owns both registration and live attempt. |
| `AuthorizationFlow` / `AuthorizationSession` / `AuthorizationInteraction` | Flow `key`, `label`, `methods`, `run`; Session `method`, `signal`, `commit`, `notify`, `prompt`; Interaction `notify`, `prompt` | These are the flow author's direct input and callback contract. |
| `Storage` / backend registry | `backend`, `register`, `mount`, `form` | A named backend and a mounted form are separate contributions. |
| `StorageBackend` / `KvFacet` / `KvUnit` | Backend `kv`, `close`; facet `open`; unit `loadAll`, `putRecord`, `deleteRecord`, `backupRecord`, `setGlobal`, `close` | Provider author implements durable operations and explicitly closes resources. |
| `SubprocessRuntime` / `SubprocessHandle` / `SubprocessOutputReader` | Runtime `resolveExecutable`, `spawn`, `spawnTerminal`; handle `stdin`, `stdout`, `stderr`, `control`, `collected`, `done`, `terminate`, `waitForExit`; reader `readFrom` | Caller owns published handle and pipe/collect read paths; range exit is separate from command outcome. |
| `ShellExecutor` / `ShellExecution` / `ShellProcess` | Executor `resolve`, `execute`; execution `result`; process `done`, `readOutput`, `observed`, `kill`, `status`, `exitCode`, `signal` | Foreground and background paths have different completion/failure contracts. |
| `PtcRuntime` / `PtcRunRequest` / `PtcBindingNamespace` / `PtcRunResult` | Runtime `resolve`, `run`; request `program`, `bindings`, `cwd`, `timeoutMs`, `sandboxPolicy`, `signal`; namespace `global`, `functions`, `errorClass`; result `value`, `logs`, `sandbox`, `error` | Bindings are direct caller input; resolved result carries program failures. |
| `SandboxProvider` / `ConfinedArgv` / `RunnerFailureRule` | Provider `confine`; confined result `argv`, `enforcement`, `denialSignatures`, `runnerFailureRules`; rule `allowedExitCodes`, `fatalSignatures`, `informationalLines` | Caller must use the wrapped command and backend-specific enforcement evidence. |

These are inclusion recommendations for the selected task, not a claim that every listed member has its own generated candidate ID. The shared ledger owner should map only IDs that exist in its inventory and retain an object-level decision for nested fields where no direct-member candidate exists.
